Group voting · Activity selection

Voting paralysis.

Three paths through the swipe pile — and a recommendation on how to stop drowning our travelers in choices.

Symptom
Participants face 30+ swipes and disengage
Target
~5 activity swipes per day of trip
Reading time
About 8 minutes
01 Diagnosis

A pile of good choices is still a pile.

Today's flow asks two consecutive piles of an unprepared brain: 27 categories first, then every activity that survives the category filter — frequently 30+ cards.

Voting is meant to be a delightful group ritual. In practice it leans toward attrition. The initiator carries the cognitive load of 27 categories; every participant then carries the load of the residual activity pool. By card #15, swipes stop encoding preference — they encode fatigue.

Hick’s Law tells us decision time grows logarithmically with the number of options. Tinder works because every card carries equivalent narrative weight; ours do not. A castle tour and a pub crawl deserve different cognitive treatment, and we are asking the same swipe of both.

02 Approaches

Three ways to thin the pile.

All three keep the swipe metaphor for activities. What changes is what the voter sees first, and how many cards they ultimately face.

A
Macro filter
Heavy data shift

Trip Vibe

Replace 27 categories with 5–6 admin-curated “vibes” picked once during trip setup.

TripSetup + Vibe → Category swipe → Activity swipe · capped

Solves

  • Eliminates the 27-category swipe entirely.
  • Vibes are mutually exclusive — no semantic overlap.
  • Cap = budget × days drops the pool to ~10–15 cards.

Cost

  • New TripVibe entity + many-to-many to Category.
  • New featured_weight per (activity, vibe).
  • Admin seeds 5–6 vibes and ranks activities inside each.

Risk

  • Categories live alongside vibes — two taxonomies to reason about.
  • Adding a new category means revisiting vibe membership.
  • Vibes are subjective; admin disagreement is likely.

Schema changes

  • + trip_vibes table
  • + trip_vibe_categories join
  • + activity_vibe_weights
B
Quantitative
Zero new data

Budget & Duration sliders

Add two pre-filters in TripSetup that prune the activity pool before any swipe begins.

TripSetup + Budget + Duration → Category swipe → Activity swipe · pre-filtered

Solves

  • Cuts pool by price band (≤€50 / €50–150 / €150+).
  • Cuts pool by duration (short / half-day / anything).
  • Zero taxonomy work — derives from existing fields.

Cost

  • Two new fields on VoteSession.
  • New params on GET /sessions/{token}/activities.
  • Two UI controls in TripSetupModal.

Risk

  • Doesn’t fix “ten castle tours within budget” homogeneity.
  • Category-swipe paralysis remains untouched.
  • Sliders feel utilitarian, not invitational.

Schema changes

  • + vote_session.budget_bucket
  • + vote_session.duration_pref
  • No new tables.
C
Hybrid
Attacks all three sources

Faster taxonomy + sliders + ranked cap

A multi-select grid replaces the category swipe, two quantitative filters live in TripSetup, and a ranked cap of ~5 activities per day surfaces the curator’s picks.

TripSetup + Budget + Duration → Category grid (multi-select) → Activity swipe · ranked + capped

Solves

  • The 27-tap swipe collapses into a single grid screen.
  • Quantitative filters cut homogeneous noise from the pool.
  • Ranked cap surfaces curator-blessed activities first.
  • Works with the existing 27 categories — no parallel taxonomy.

Cost

  • + activity.featured_weight (int, default 0).
  • + budget_bucket, duration_pref on VoteSession.
  • Replace CategoryVotePage with a CategorySelectPage grid.
  • Admin column for featured_weight in the activity list view.

Risk

  • Multi-select grid loses the playful swipe affordance on step one.
  • Curators must keep featured_weight meaningful over time.

Schema changes

  • + activities.featured_weight
  • + vote_session.budget_bucket
  • + vote_session.duration_pref
03 Recommendation

Ship C.

Why C, in one line

The only path that attacks all three sources of fatigue without inventing a second taxonomy.

01

Removes an entire screen of paralysis

Swipe-on-categories becomes tap-to-toggle. Twenty-seven micro-decisions collapse into a single glance and a few selections.

02

Adds two cheap, orthogonal filters

Budget and duration derive from fields the activity already carries. No new admin work; immediate pool reduction at zero schema cost.

03

Adds an editorial lever

One integer per activity gives curators a quality knob. The top-N feels handpicked, not exhaustive — the difference between a menu and a tasting.

Why not A

Two taxonomies are heavier than one.

Trip Vibe is elegant in isolation but doubles the admin surface — every new category demands a vibe-membership decision, and the existing 27 categories don’t gracefully retire. A is a candidate for v2 once traffic reveals which vibes actually cluster.

Why not B

It leaves the loudest pain untouched.

B is cheap but only addresses one of the three fatigue sources. Participants still swipe 27 categories, and a budget-filtered pool of 20 castle tours still looks like 20 castle tours. B is a strict subset of C — there’s no reason to ship it standalone.
